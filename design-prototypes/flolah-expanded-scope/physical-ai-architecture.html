What “Edge Hub” means

The host plus its local gateway services. For initial testing the host is your Windows laptop; for a dedicated site deployment it can be a Linux mini PC or Raspberry Pi. Arduino/ESP32 is an optional device endpoint, not required hub hardware.

  • One deployment per physical site. Enroll each hub to a tenant and site; associate assets with that hub.
  • No full cloud-stack copy. AI reasoning and company orchestration can stay on the VPS.
  • Persist locally: hub identity/credentials, policy cache, operation journal, HA configuration, broker data and simulator state. Keep the laptop awake during test runs.
  • Keep offline rules explicit. Only previously approved safe local routines continue; full offline AI chat is not assumed.

Docker and network boundaries

  • Separate deployments: cloud services on the VPS; edge services on the laptop or site computer. Linux containers on Windows use the selected compatible runtime; HA OS may use a separate VM.
  • Home Assistant Container: use the documented Linux networking configuration. Host networking exposes host interfaces, so restrict access appropriately.
  • Gateway → HA: use an explicit host/LAN address. A container’s localhost does not refer to another container.
  • MQTT: private network/listeners, authentication and topic ACLs. Host-networked HA requires an explicit route or restricted listener to reach a bridge-networked broker.
  • Radio protocols: Zigbee, Thread and Z-Wave need supported hardware/controller pathways. Containers do not supply the radio.

12–16. The return path is as important as dispatch

Device state/event → MQTT broker → Home Assistant → HA adapter → gateway journal and event buffer → authenticated hub connection → Flolah operation/evidence validation → audit + workflow status → human notification or exception.

Flolah completes the operation only when the required observed evidence matches the asset, operation, expected result and permitted time window. Timeouts and uncertain results remain visible. Reconnects replay evidence and query outcomes; they do not blindly replay actuator commands.

End-to-end sequence and correlation
  1. Request: a human gives an outcome through a client, including Android if used as a UI.
  2. Plan: an AI employee or workflow selects a supported capability, not arbitrary protocol payloads.
  3. Authorize: cloud policy and human approval gates apply before dispatch.
  4. Record: persist the operation ID, asset, adapter/version, input, deadline and decision.
  5. Route: use the enrolled hub's outbound-authenticated connection. Each hub belongs to a tenant and site.
  6. Check locally: edge verifies authority, capability version and expiry and journals before execution.
  7. Translate: the selected adapter maps normalized capability inputs to its supported protocol or SDK.
  8. Execute: device/controller performs the bounded action; independent equipment safety remains in control.
  9. Observe: state/progress/outcome travels back over the appropriate API, MQTT topic or robot action feedback.
  10. Normalize: adapter translates observations/errors into Flolah events with correlation and timestamps.
  11. Persist and reconcile: edge buffers evidence during disconnection and forwards it on recovery.
  12. Verify and report: cloud validates evidence, updates audit/workflow state, and reports completion or the required human intervention.
Android deployment decision / three distinct roles

Will the edge be an Android app?

It can be a future native Android Edge app, but that APK is not implemented in Phase 1. The implemented gateway is Node.js for the laptop/site host. Android needs a native runtime implementation of the same cloud wire contracts, policy/journal semantics and adapter conformance tests; the current Docker/Node package is not an Android installation package.

Android client — no edge role

Phone/tablet/TV requests work, shows progress and collects approvals. The site gateway executes device work. MQTT broker and HA server stay on the site host. This is the recommended initial Android role.

Android Edge app — future option

Native app contains hub identity, secure credential storage, cloud transport, local policy checks, durable queue/journal, and curated native adapters. It can use an MQTT client library, supported Bluetooth APIs or vendor SDKs. Its availability is subject to Android service, battery, permission and background-start restrictions; it is not an assumed always-on Linux replacement.

Android device or robot endpoint

An Android-based robot, kiosk or phone can expose an approved vendor API or companion endpoint to a separate site hub. Its Android OS does not automatically make it a Flolah hub or a task-owning physical agent. A native device-side app/SDK is possible only where the vendor permits installation and the necessary APIs exist.

If the robot also hosts a validated Android Edge app, it may combine gateway and endpoint roles. Keep those identities, permissions and controller boundaries separate. This is a future supported-device integration, not universal robot compatibility.

Where does MQTT run when Android is involved?

  1. Android is only a UI: MQTT stays entirely between the site hub/broker and MQTT-capable equipment. Android does not need MQTT.
  2. Android is an edge or device endpoint: an MQTT client can run inside the native app. The broker runs on an existing site computer/gateway, NAS or suitable dedicated host.
  3. Android-only site, no local broker: use an explicitly configured authenticated TLS cloud broker if MQTT is necessary. It can be a dedicated broker container on the Flolah VPS or a managed service, separate from the existing backend; that cloud broker deployment is not part of the implemented Phase 1 configuration. Android and MQTT devices must independently reach that broker. This introduces internet dependence; local offline MQTT operation is unavailable if no broker is reachable.
  4. Direct Bluetooth/vendor API: MQTT is optional and may be absent. A supported Android adapter can communicate directly with the endpoint; the cloud-to-edge control channel remains authenticated WSS.
No MQTT broker or Home Assistant server is assumed inside the Android APK.

MQTT is a messaging protocol, a client is a library, and a broker is a separate service. Home Assistant's Android Companion app is a client of an HA server; it does not replace that server. Embedding a broker in Android would be a separate evaluated product choice, not the default architecture.

For a public MQTT broker deployment use TLS, per-client credentials, tenant/site/device topic ACLs and lifecycle/revocation controls. A cloud MQTT broker is optional device transport, separate from Flolah's hub control connection. Do not expose the Phase 1 local lab broker publicly.

Architecture decision / shared semantics, pluggable translation

One physical capability layer. Reusable adapter plugins.

Human / AI employee / workflow
↓ Vendor-neutral capability request
Capability API → authorization → shared task/operation lifecycle → enrolled hub → adapter framework

Common Flolah logic

Tenant/site identity, registry, schemas, permission/approval decisions, operation/task records, deadlines, evidence, audit, retry rules and reconciliation contracts. Reuse these across every adapter.

Adapter-specific translation

Discovery, pairing, credentials, vendor command mapping, events/errors, connectivity and supported cancellation/deduplication. Equipment retains real-time control and safety.

Reusable adapter families: Simulator/MQTT · Home Assistant · vendor robot API · ROS 2

An existing compatible adapter needs configuration, not new core logic. A different model may need a capability profile; a new vendor interface needs an adapter. New physical functions may require new capability definitions. A common protocol alone does not imply common task meanings.

Adapter manifest and contract

Manifest: adapter ID/version, supported profiles/models, canonical capabilities, configuration schema, credential requirements and declared limitations. Curate adapters before installation; do not download or execute code supplied by discovered devices.

Contract: discover → pair → describe → readProperty / invokeAction / subscribe → health. Optional task contract: startTask / getTask / cancelTask. Declare which operations are unsupported, how idempotency works and what evidence establishes completion. Adapters cannot bypass core/edge policy.

Example: clean an area without vendor logic in the workflow

Common request: clean_area(areaId, operationId). Vendor A maps the area to its zone ID; Vendor B maps it to a map segment; the simulator creates a controlled task. Each returns normalized progress and outcomes. The business workflow remains the same. Unsupported cleaning/cancellation must be reported rather than silently approximated.

Onboarding decision / discovery does not grant authority

Register a robot or simulated physical agent

  1. Enroll the hub: claim its authenticated identity to a household/company and site.
  2. Select an approved adapter: discover compatible assets or add an explicit endpoint/vendor connection. The simulator follows the same flow with clearly marked synthetic assets.
  3. Pair and authorize: the owner completes pairing and grants connection access. Store device credentials in the protected site credential store.
  4. Normalize capabilities: obtain actions, observations, tasks and limitations. Validate descriptions and assign risk/policy classifications.
  5. Register PhysicalEntity: record asset ID, vendor/model/profile, location, tenant/site, hub, adapter/version, capability description and connectivity.
  6. Enable PhysicalAgent only when justified: delegated task responsibility and observable outcomes are required. A command-only switch or sensor remains a PhysicalDevice.
  7. Apply operating policy: set allowed operations, approval requirements, location/time bounds, accountable owner and revocation rules.
  8. Run controlled validation: verify identity, an allowed capability, observed results and failure handling before enabling work. Revalidate changed capabilities or adapter versions.
Phase 1 / hardware-free integration acceptance

One simulator, repeatable scenarios

Three reusable profiles

  • Switch/light: on/off action with independently observed state and configurable delays.
  • Sensor: adjustable temperature, motion or battery readings; stale values and offline events.
  • Robot task: simulated acceptance, progress, completion, cancellation and failure. Contract coverage for Phase 2, not real robot validation.

Test stages

  1. Local gateway → MQTT broker → simulator.
  2. VPS enrollment/registry/policy → laptop gateway → same simulator.
  3. Home Assistant adapter → same broker and simulated assets.
  4. Repeat fault/restart scenarios and collect evidence.
  1. Success: authorized operation completes only after correlated observed state arrives.
  2. Policy: unauthorized/cross-tenant operations are denied; approval-required work never dispatches prematurely.
  3. False success: accepted command without a state change times out or remains uncertain.
  4. Stale evidence: delayed/out-of-order observations do not complete a newer operation incorrectly.
  5. Duplicates: repeat an operation ID and lose acknowledgements; validate declared deduplication without claiming exactly-once physical execution.
  6. Failures: disconnect simulator, broker or cloud and expose an actionable exception.
  7. Restart recovery: preserve journals, reconcile state and avoid blind replay.
  8. Offline authority: only safe pre-approved routines with valid cached policy continue; no new cloud dispatch while disconnected.
  9. Invalid input: reject unsupported capabilities, malformed commands, revoked credentials and expired authorization.
  10. Task contracts: verify progress, timeout, cancellation and terminal outcomes with the robot profile.
Evidence per scenario

Fixture/software versions, simulated profile, tenant/site/hub/asset IDs, operation ID, policy decision, dispatch/acknowledgement/observation timestamps, expected-versus-actual assertions, final status and recovery history. No credentials in logs. AI interpretation is assessed separately from deterministic protocol and policy assertions.

Boundary: simulator results validate orchestration, policy, transport, adapters and recovery. They do not establish vendor compatibility, radio discovery, actuator safety or real-world performance. A later hardware pilot must validate those before production physical readiness. Replace adapters, retaining the common capability contracts and contract tests.

Implementation decisions

Recommended Phase 1 deployment

Use the Windows laptop, Flolah Edge Gateway, one MQTT broker and a generic software simulator. First validate the direct MQTT path; then add Home Assistant adapter acceptance against the same simulated assets. No equipment purchase or Android bridge is needed. Gateway/cloud physical modules, curated adapters and simulator are implemented in the repository behind an opt-in feature flag. The laptop lab is runnable without Docker; real Home Assistant acceptance has passed the cloud-to-edge-to-HA path with simulated equipment in an isolated environment. Production rollout and real-equipment validation are separate gates. Real robot adapter/task integration remains Phase 2.

Why not put the gateway beside all the VPS containers?

The remote VPS is outside the site’s local device network. It cannot automatically discover LAN-only equipment or access local USB radios. Remote vendor-cloud integrations may be possible, but do not replace a local gateway for local execution and outage handling. If the entire Flolah platform is self-hosted on-site, the services can physically share a Linux host while retaining their logical boundaries.

Home Assistant OS versus Home Assistant Container

Home Assistant generally recommends HA OS for its own managed experience. For a shared Flolah-managed Linux host, HA Container lets Flolah run alongside it. Container does not include HA OS apps; required helpers must be managed separately. Reuse an existing HA OS appliance instead of treating it as a general-purpose Docker host.

What does Android do?

Android/TV can be a human client. A future native Android Edge APK can implement the same cloud contract for supported capabilities, with native adapters and lifecycle constraints; that APK is not part of the implemented Phase 1 package. Android can also be a device/robot endpoint behind a separate gateway. MQTT clients may run in Android apps, but the broker and any HA server remain separate services. See the Android round-trip section above.

Phase 1 software is implemented as an opt-in pilot with a Windows-compatible simulator lab. Existing production functionality is unchanged. Simulator/protocol acceptance does not certify real equipment; real Home Assistant integration acceptance passed; production rollout and real hardware compatibility remain separate gates.
